# GridSense API — Read Layer (Phase 4)

A thin, typed, read-only HTTP API over the Gold marts built by the
dbt project in `../transform/`. Every endpoint maps to exactly one
Gold table — no business logic lives here, only filtering,
pagination, and response typing via [FastAPI](https://fastapi.tiangolo.com/)
and [Pydantic](https://docs.pydantic.dev/).

## Endpoints

| Method | Path | Reads from | Description |
|---|---|---|---|
| GET | `/health` | — | Liveness + DB connectivity check |
| GET | `/api/v1/kpis/daily` | `gold.mart_grid_kpis_daily` | Daily system-level KPIs |
| GET | `/api/v1/voltage/hourly` | `gold.mart_voltage_quality_hourly` | Hourly voltage KPIs per bus |
| GET | `/api/v1/voltage/violations` | `gold.mart_voltage_quality_hourly` | Worst voltage-violation rates, sorted |
| GET | `/api/v1/lines/hourly` | `gold.mart_line_loading_hourly` | Hourly loading KPIs per line |
| GET | `/api/v1/lines/overloaded` | `gold.mart_line_loading_hourly` | Lines with active overload events, sorted |

All list endpoints accept `network` (filter), plus a resource-specific
filter (`bus_id`, `line_id`, or `min_rate`) and `limit` for pagination.
Interactive docs — try every endpoint from the browser — are
auto-generated by FastAPI at **http://localhost:8000/docs**.

## Requirements

- Python 3.10+
- A running TimescaleDB instance with the Gold marts already built
  (see the root README and `../transform/README.md`)

## Setup

```bash
pip install -r requirements.txt
```

Connection details are read from the same environment variables used
across the project (defaults match the root `docker-compose.yml`):

```bash
export TIMESCALE_HOST=localhost
export TIMESCALE_PORT=5432
export TIMESCALE_USER=postgres
export TIMESCALE_PASSWORD=postgres
export TIMESCALE_DB=gridsense
```

## Run

```bash
uvicorn app.main:app --reload --port 8000
```

Or from the project root: `make api-run`.

Then open http://localhost:8000/docs.

## Test

```bash
pytest -v
```

15 tests, all using a fake DB session (`tests/conftest.py`) — no
live database or Docker required. Each test asserts both the response
shape and, where relevant, that filter parameters were correctly
passed through to the underlying SQL.

## Design notes

- **One endpoint, one table.** Keeping the mapping 1:1 with the Gold
  layer means there's never a question of "where does this business
  rule live" — it's always in the dbt model, never duplicated here.
- **Parameterized queries throughout.** Every filter uses SQLAlchemy
  bound parameters (`:network`, `:bus_id`, ...), never string
  interpolation — safe against SQL injection by construction, not by
  discipline.
- **`/health` never raises.** A database outage is reported as a
  normal `200` response with `"database": "unreachable"`, so
  monitoring/orchestration tools can distinguish "the API process is
  down" (no response at all) from "the API is up but its dependency
  is down" (this case) — an important distinction for anyone running
  this behind a load balancer or Kubernetes liveness probe.
