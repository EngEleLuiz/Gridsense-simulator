# Phase 7.4 — Three-phase hosting capacity (UK feeder) and new dashboards

Branch `phase-7.4-unbalanced`.

## Three-phase hosting capacity

The study runs on `hosting_capacity/unbalanced.py` with pandapower `runpp_3ph`, for networks whose customers are single-phase `asymmetric_load` elements.

**Networks.** The IEEE European LV test feeder (UK) is registered in two snapshots:

| Key | Snapshot |
|---|---|
| `ieee_european_lv_offpeak` | off-peak, minute 1440 |
| `ieee_european_lv_onpeak` | on-peak, minute 566 |

Both have 906 LV buses and 55 customers.

**Phase models.** Both use the same solver:

| Model | Load and PV |
|---|---|
| `unbalanced` | Each customer's load and PV stay on the customer's own phase |
| `balanced_equivalent` | Load and PV are spread evenly over the three phases, with each total unchanged |

The difference between the two isolates the effect of unbalance.

**Units and checks.**
- PV is allocated equally per customer: λ is **kWp per customer**. `total_pv_mw` is the quantity that compares across networks.
- The voltage band and the line and transformer limits come from the usual frameworks.
- The voltage unbalance factor (VUF) is reported; it can be enforced with `max_vuf_percent`.
- `source_vm_pu` overrides the feeder's source voltage, which is specified at 1.05 pu.

**Methods.** Deterministic and stochastic (random single-phase adopters, α-quantile with a distribution-free CI). QSTS on three-phase networks is rejected with a clear message: the pandapower feeder ships three snapshots, not time series.

**Runner.**
- New options: `--phase-model`, `--source-vm-pu`.
- For three-phase networks the `--load-scale` default is 1.0, so the snapshot is used as is.
- New payload fields: `phase_model`, `lambda_unit`, `pv_mw_per_phase`, `max_vuf_percent`, `source_vm_pu`.
- New payloads replace inf/NaN with null, because PostgreSQL JSONB rejects `Infinity` and `NaN`.

### Results (preliminary, measured)

| Snapshot / criterion / source | Unbalanced (kWp per customer) | Balanced equivalent | Balanced overestimate |
|---|---|---|---|
| Off-peak, EN 50160, 1.05 pu | 2.78 | 3.50 | +26 % |
| Off-peak, EN 50160, 1.00 pu | 5.34 | 6.06 | +13 % |
| Off-peak, PRODIST, 1.00 pu | 2.66 | 3.34 | +26 % |
| On-peak, EN 50160, 1.05 pu | 3.31 | 4.41 | +33 % |

- **The balanced model overestimates the capacity by 13–33 %.** This is consistent with the literature: balanced studies underestimate voltage problems.
- **The source voltage dominates.** Going from 1.05 to 1.00 pu roughly doubles the capacity.
- **Under PRODIST at the specified 1.05 pu source, the on-peak snapshot already violates without any PV**, reaching 1.068 pu on phase c from neutral-point shift on a lightly loaded phase. The balanced model does not see it and reports 1.03 kWp per customer.

## Five new Grafana dashboards (replace the three old ones)

They are generated by `scripts/build_grafana_dashboards.py`:

| UID | Content |
|---|---|
| `gridsense-01-telemetry` | Load, generation, load factor, contingencies, line loading |
| `gridsense-02-voltage` | Violation rate, voltage envelope, worst buses (in-scope buses only) |
| `gridsense-03-hc-methods` | Latest comparable result per method, criterion and operating point; binding constraints; non-comparable runs and why |
| `gridsense-04-hc-duration` | QSTS per criterion and series; duration gain over τ = 0; per-bus verification; weekly capacities |
| `gridsense-05-network-panel` | Capacity across networks, binding-constraint mix per framework, unbalance effect |

Dashboards 4 and 5 read the untyped fields straight from `bronze.hosting_capacity_results.raw_value`.

## Validation done in the development sandbox

**Real PostgreSQL 16 database.** It held:
- the Gold tables with exactly the dbt column definitions (synthetic telemetry rows);
- 18 **real runner payloads**: the deterministic panel, the three-phase UK runs, a stochastic run, and QSTS with PRODIST and zero-tolerance criteria on SimBench with its own profiles.

| Check | Result |
|---|---|
| Payload load into JSONB | 18/18 loaded, none rejected |
| Real dbt build of `stg_hosting_capacity_results` and `mart_hosting_capacity` | 16/16 passed, including the bracket-order and comparable-row tests: duration-criterion and three-phase rows flow through dbt unchanged |
| Every dashboard query and variable executed | 30/30 OK; one panel correctly empty (no non-comparable runs) |

**Caveat.** Plain PostgreSQL was used, not TimescaleDB. The queries use no Timescale-specific functions.
